# Event Catalog — t3n-nexus

Liệt kê toàn bộ domain event lưu chuyển qua Kafka giữa các services.
Hiện sự kiện là JSON, tiến hoá theo kỷ luật chỉ thêm trường kèm `version`; hướng nâng cấp là Confluent Schema Registry (Avro), xem `tech-stack.md`.

## Quy ước

- **Topic**: `{producer}.{entity}.{past-tense-verb}` — ví dụ `order.order.created`
- **Payload**: chỉ liệt kê các field có ý nghĩa inter-service — field nội bộ không đưa vào event
- **Pattern**: `Saga` = tham gia vào choreography saga; `Notify` = trigger Notification BC; `Projection` = cập nhật read model / search index; `CDC` = Debezium đọc binlog

## Khung thông điệp và hàng chờ lỗi (ADR-0008)

- Mọi event ghi qua hộp thư (`outbox-starter`) đi trên bus trong **một khung JSON chung**: `eventId`, `eventType`, `occurredAt`, `aggregateId`, `aggregateType`, `schemaVersion` (số nguyên từ 1), `traceId` và `spanId` (tùy chọn), `payload`. Hợp đồng khung ở `common-events`; phần "Payload" của từng event liệt kê ở dưới là nội dung của `payload`. Chỉ thêm trường; đổi nghĩa thì tăng `schemaVersion`. Bên nhận bỏ qua trường lạ. Không đưa dữ liệu định danh hay bí mật vào `payload` (thư viện từ chối theo tên trường).
- **Khóa thông điệp** là `aggregateId`, ghi dạng JSON có dấu nháy (`"K4"`). Thứ tự chỉ được bảo đảm cho các event của một thực thể **trong cùng một chủ đề**.
- **Bên nhận** dùng `event-consumer-starter`: ack sau khi handler trả về, thử lại tối đa 3 lần (1 giây, nhân đôi, trần 30 giây), hết lượt hoặc lỗi không thể thử lại thì chuyển sang hàng chờ lỗi của dịch vụ (`<spring.application.name>.dlq`, ghi đè được bằng `app.event-consumer.dlq-topic`; ADR-0010) giữ nguyên khóa và giá trị, thêm tiêu đề `x-dlq-error-class` và `kafka_dlt-original-topic`; ghi ERROR `EVENT_DEAD_LETTERED` và tăng bộ đếm `events.dead_lettered` theo chủ đề. Xử lý lại từ hàng chờ lỗi là thủ công.
- Bảng "DLQ Topics" ở cuối file là danh sách hàng chờ lỗi theo quy ước một hàng chờ lỗi cho mỗi dịch vụ nhận; `event-consumer-starter` cài đúng quy ước này (ADR-0010). Dịch vụ nào cần tách (như `email-worker` theo tier) đặt `app.event-consumer.dlq-topic` và ghi vào bảng.

## audit-service

Nhật ký kiểm toán chỉ **nhận**, không phát event nào. Các BC khác ghi `AuditActionRecorded` qua thư viện `audit-events` (`AuditRecorder`, cùng giao dịch với hành động, qua hộp thư ADR-0008).

| Event | Topic | Producers | Consumers | Pattern | Key Payload |
|-------|-------|-----------|-----------|---------|-------------|
| `AuditActionRecorded` | `audit.action.recorded` | mọi BC có hành động cần truy vết (C1a: seller-service, catalog-service) | audit-service | Ghi nhật ký | `sourceService`, `actor` (`accountId`, `role`), `action`, `target` (`type`, `id`), `details` |

- **Khóa thông điệp** là `aggregateId` của khung (mã đối tượng bị tác động), nên các hành động lên cùng một đối tượng đến theo thứ tự.
- **`actor`:** `accountId` bắt buộc trừ khi `role` là `SYSTEM`. Là bản chụp tại lúc làm, bên nhận không tra lại.
- **`details`:** phẳng, tối đa 10 khóa, tên khóa `^[a-z][A-Za-z0-9]{0,39}$`, giá trị chuỗi (tối đa 500 ký tự), số hoặc đúng/sai. Tên khóa nhạy cảm bị bỏ (bên phát ném lỗi, bên nhận bỏ khóa và cảnh báo). Mỗi BC phát tự khai báo hành động và khóa dữ kiện của mình.
- **Khử trùng:** theo `eventId` của khung, lưu thành `source_event_id` có ràng buộc duy nhất ở Nhật ký. Hàng chờ lỗi: `audit-service.dlq` (ADR-0010); chủ đề gốc ở tiêu đề `kafka_dlt-original-topic`.
- Chi tiết: `stage/c1a-listing/02-audit-log/tech.md` T2, T5; ADR-0009.

Ảnh trong bản chụp mang khóa đối tượng, bên nhận ghép URL. `inventory-service` hiện nghe các chủ đề cũ `catalog.variant.*`, `catalog.product.*`: viết lại ở C2a.

## scheduler-service

| Event                    | Topic                  | Consumers                                                       | Pattern | Key Payload                                    |
|---------------------------|-------------------------|--------------------------------------------------------------------|---------|-------------------------------------------------|
| `ScheduledJobFiredEvent` | `scheduler.job.fired`  | `customer-service`, `cart-service`, `payment-service`, `order-service`, `inventory-service` (theo `taskType`) | Notify  | `scheduledJobId`, `instanceId`, `taskType`, `payload` |

**`order-service`** — 2 `taskType` riêng cho cơ chế `CREATED`-timeout (xem `feature/07-place-order/implementation.md` Phase 5, quyết định đảo ngược 2026-09-21): `ORDER_INVENTORY_TIMEOUT_REDIS_SCAN` (Lớp 1, đọc Redis ZSET) và `ORDER_INVENTORY_TIMEOUT_DB_SCAN` (Lớp 2, backstop query bảng `orders`). Cả 2 đều recurring, không mang `payload` nghiệp vụ — thuần tín hiệu "tới giờ quét", `order-service` tự query lại state của chính nó, đúng nguyên tắc chung của `ScheduledJobFiredEvent`.

**`inventory-service`** — 2 `taskType` riêng cho TTL self-guard trên `Reservation` (2026-09-22, cùng lý do với `order-service` ở trên): `RESERVATION_TIMEOUT_REDIS_SCAN` (Lớp 1) và `RESERVATION_TIMEOUT_DB_SCAN` (Lớp 2, backstop query bảng `reservation`). `@KafkaListener` phía `inventory-service.ScheduledJobFiredConsumer` đang comment — chưa đăng ký 2 job này qua Admin API.

`instanceId` — id của `ScheduledJobInstance` (aggregate riêng, 1 record cho mỗi lần fire) vừa dispatch cho lần fire này. Consumer mang nguyên `instanceId` khi callback báo outcome — không dùng `scheduledJobId` vì 1 recurring job tạo nhiều instance khác nhau theo thời gian.

### Consumes — callback outcome (contract phía scheduler-service, topic cụ thể do từng producer đặt tên)

`scheduler-service` consume 1 event khi consumer (`customer-service`/`cart-service`/`payment-service`) xử lý xong `ScheduledJobFiredEvent` — cập nhật `ScheduledJobInstance.status` (SUCCEEDED/FAILED), **không** ảnh hưởng `ScheduledJob.status`/`nextFireAt` (xem `service.md` §Callback). Contract tối thiểu — tên topic + tên event cụ thể do mỗi producer tự đặt theo convention của chính BC đó (`{producer}.{entity}.{past-tense-verb}`), **chưa chốt** — cần làm khi implement Phase 3+ của từng consumer:

| Field         | Type                 | Ghi chú                                        |
|----------------|----------------------|--------------------------------------------------|
| `instanceId`       | string               | Bắt buộc — khoá để load đúng `ScheduledJobInstance`  |
| `outcome`     | `SUCCEEDED \| FAILED` | Bắt buộc                                        |
| `failureReason` | string, nullable   | Chỉ có khi `outcome=FAILED`                     |
| `completedAt` | Instant              | Bắt buộc                                        |

**Khuyến nghị partition key = `instanceId`** cho mọi producer khi chốt topic — Kafka đảm bảo mọi message cùng `instanceId` (kể cả redelivery) vào cùng 1 partition, xử lý tuần tự bởi đúng 1 consumer, loại bỏ race 2 message cùng `instanceId` được xử lý đồng thời ở `scheduler-service`. Đây là khuyến nghị **cộng thêm**, không phải điều kiện đủ — `scheduled_job_instance.version` (`@Version`, xem `service/scheduler-service/data.md` §Locking) là lớp phòng thủ chính, tự scheduler-service kiểm soát và verify được, không phụ thuộc producer làm đúng convention này hay không.

## Ghi chú Saga Flow

> **Yêu cầu bắt buộc với volume lớn:**
> - **Outbox Pattern** trên mọi event publish — ghi vào bảng `outbox` cùng transaction, Debezium push lên Kafka
> - **Idempotency** tại mọi consumer — dedup theo `eventId`, lưu `processed_event_id`
> - **Kafka partition key = `orderId`** — đảm bảo ordering cho mọi event của cùng một saga

### Tạo đơn hàng (Happy Path) — fully async, không có sync call
```
order-service         inventory-service      payment-service       fulfillment-service
      |                      |                     |                      |
      |-- OrderCreated -----> |                     |                      |
      | <-- InventoryReserved |                     |                      |
      |-- PaymentRequested -------------------- >   |                      |
      |                      |               <process async>               |
      | <-- PaymentSucceeded ------------------- -- |                      |
      |-- OrderConfirmed -------------------------------------------- > |  |
```

### Reservation thất bại (Compensating)
```
order-service         inventory-service
      |                      |
      |-- OrderCreated -----> |
      | <-- InventoryReservationFailed
      |-- OrderCancelled (payment không được trigger)
```

### Thanh toán thất bại (Compensating)
```
order-service         inventory-service      payment-service
      |                      |                     |
      |-- OrderCreated -----> |                     |
      | <-- InventoryReserved |                     |
      |-- PaymentRequested -------------------- >   |
      | <-- PaymentFailed ---------------------- -- |
      |-- OrderCancelled ----> |
      |                       | [release reservation]
```
